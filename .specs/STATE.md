O repository aplica o filtro e responde 404 fora da carteira; o RLS não filtra carteira. `Contact.ownerId` e `Conversation.assigneeId` são `userId` de um `Member` da mesma organização (FK composta `(organizationId, ownerId) → Member(organizationId, userId)`). A transferência de carteira soma os `portfolioMoves` que o `app.ts` entrega a `memberRoutes`; hoje só `moveContactOwner` (contatos de X passam a Y) | active | `.specs/features/conversation-core/plan.md` (Landing 8, 9) |
| AD-015 | Contrato do canal com o domínio de conversa (ADR-013). Todo canal entra por `receiveInbound(deps, tenant, { channelId, externalId?, fromPhone, kind: TEXT \| UNSUPPORTED, text?, sentAt })` → `{ conversationId, messageId, created }`: telefone normalizado ali para E.164 (`shared/phone.ts`, `libphonenumber-js/max`, Brasil padrão; inválido → `422 INVALID_PHONE`); texto de 1 a 65 536 caracteres (`422 INVALID_MESSAGE`); acha, reabre (mesma linha, `handler = reopenHandler`, nunca o humano anterior, auditoria `conversation.reopen` com autor `SYSTEM`) ou cria a conversa; trava a linha (`FOR UPDATE`) e grava `seq = lastSeq + 1` com `INSERT … ON CONFLICT ("organizationId", "channelId", "externalId") WHERE "externalId" IS NOT NULL DO NOTHING`; um duplicado desfaz a transação inteira e devolve a mensagem guardada com `created: false`. A saída é `sendMessage(deps, tenant, { conversationId, sender, text })`, com a regra `canSend` como condição do `UPDATE` que reserva o `seq` (0 linhas → `404 NOT_FOUND`, `409 CONVERSATION_CLOSED` ou `409 NOT_HANDLER`); `WAITING` na saída; `deliveryStatus` por `channel.kind` (`WEB_CHAT` → `SENT` na transação). Transições em `conversations/conversation-state.ts`, funções puras; `aiAvailable()` devolve `false` até a F4 | active | `.specs/features/conversation-core/plan.md` (Landing 3, 4, 5, 6) |
| AD-016 | Backfill de tabela com RLS numa migration. O dono das tabelas roda as migrations; com `FORCE ROW LEVEL SECURITY` o RLS vale para ele quando não é superuser (hoje é: `POSTGRES_USER`). Padrão: um único `DO $$ … $$` (atômico) que tira o `FORCE` só da tabela lida enquanto lê os ids (`ALTER TABLE … NO FORCE` / `FORCE` no mesmo bloco) e grava cada linha com `set_config('app.tenant_id', <org>, true)`, passando pelo `WITH CHECK` da política, sem exceção na política; zera o `app.tenant_id` no fim. A prova roda a migration com um dono `NOSUPERUSER NOBYPASSRLS` (`withSchemaBefore(…, { owner })`), porque como superuser um `INSERT … SELECT` ingênuo passaria e, sem superuser, criaria zero linhas sem erro | active | `.specs/features/conversation-core/plan.md` (Landing 7) |
| AD-017 | Composição entre módulos sem ciclo. O `organizations` (que exporta `requireTenant`/`requirePermission`, importados pelas rotas de todos os módulos) não importa módulo de domínio: o `app.ts` lhe entrega `setupOrganization` (passos do onboarding na mesma transação; hoje `createDefaultChannel`) e `portfolioMoves`.
